# LCD 1キーゲーム (Step 7: ランダムな点を追加)

MAX 10 (10M08SCE144C8G, CQ-MAX10-A + Pmod ボード) と
PMOD-TFTLCD v1.1 (ILI9341, 320x240) を使った FPGA デザインです。

**320x240 の 1bit Frame Buffer を持ち、その上で 1 キーのラインゲームを
動かします。ただし Frame Buffer は「当たり判定」専用で、LCD の表示には
使いません。**

## Step 7 で変えたこと（ランダムな点）

初期化処理の最後に、**2x2 の点を 20 個**疑似ランダムな位置に描きます
(`prompt.txt` #5)。

| 項目 | 値 |
|---|---|
| 点のサイズ | 2x2 ドット |
| 個数 | 20 個 |
| 位置の範囲 | (2,2)-(318,318) で指定 → **Y はパネルの高さに合わせて 238 にクランプ** |
| 色 | 紫 `16'hF81F` (`COLOR_DOT`) |
| 乱数 | 32bit LFSR (Galois, タップ 32/22/2/1, 周期 $2^{32}-1$) |
| 生成方法 | 棄却サンプリング（剰余演算・除算を使わない） |

点は Step 6 の罫線・動く線と同じく**2 か所に描きます**。

| 出力先 | 内容 | 役割 |
|---|---|---|
| Frame Buffer | 点の 4 ピクセルのビットを 1 に | 当たり判定（点にぶつかると GAME OVER） |
| LCD | `(x,y)-(x+1,y+1)` の 2x2 矩形 | 表示（紫） |

---

## 起動シーケンス（= ゲームの初期化処理）

1. Frame Buffer を全クリア（当たり判定モデルを空にする）
2. **LCD 画面全体をオレンジで塗りつぶす**（1 回の矩形書き込み）
3. 以下の 9 本の赤い水平線を、Frame Buffer と LCD の両方に描く
4. **2x2 の紫の点を 20 個、疑似ランダムな位置に描く**（Frame Buffer と LCD の両方）
5. ゲーム開始

```
(0, 25)-(279, 25)      (40,  50)-(319,  50)
(0, 75)-(279, 75)      (40, 100)-(319, 100)
(0,125)-(279,125)      (40, 150)-(319, 150)
(0,175)-(279,175)      (40, 200)-(319, 200)
(0,225)-(279,225)
```

## ゲーム（`game_ctrl.sv`）

初期化が終わるとゲームが始まります。1 ドット幅の線が
**フレーム周期の整数倍ごとに 1 ドット** (既定で約 250 ms に 1 ドット)
伸びていきます。間隔は `STEP_MS` をフレーム周期に丸めた値です (§5.2)。

| 操作 | 動き |
|---|---|
| ボタン (PIN_62) を押していない | 右下方向に伸びる |
| ボタン (PIN_62) を押している | 右上方向に伸びる |
| x=319 にぶつかる | 横方向だけ反転 |
| x=0 にぶつかる | 横方向だけ反転 |
| 描く前に Frame Buffer を読んで既に描かれていた | **GAME OVER**（そこで停止） |

開始座標は (1,1) です。

**動作確認済み:**

| 検証 | 結果 |
|---|---|
| `tb_framebuffer` | PASS (153,604 チェック) — 全アドレス/ビットの対応と読み出しレイテンシ |
| `tb_line_draw` | PASS (10 ケース) — 全ワード比較 + **LCD 行リクエストの内容** |
| `tb_dot_field` | PASS (7 ケース) — **LFSR の数列**、範囲、2x2 の形、バッファ内容 |
| `tb_game` | PASS (8 ケース) — ゲームの全ルール + **ドットごとの 1x1 LCD リクエスト** |
| `tb_rect_write` | PASS — 初期化 67 バイト、矩形書き込み、1x1 ドット、バス停止 |
| `tb_spi_clk` | PASS — SPI 分周器が正確に 10.00 / 12.5 MHz |
| Quartus コンパイル | 成功 0 errors, 8 warnings |
| メモリ | **76,800 bit = 320×240 の 1 面分** (M9K 16 ブロック, 38 %) — Step 5 の半分 |
| ロジック | 1,347 LE (17 %) / 623 レジスタ |
| タイミング | セットアップ Slack **+7.980 ns**、ホールド +0.360 ns |

## 2. データの流れ

```
clk(50MHz) ─► reset_sync ─► rst
                              │
     ┌────────────────────────┴──────────────────────────┐
     │                                                   │
     ▼                                                   ▼
 framebuffer (320x240x1)                        起動シーケンス
   │  ▲  ▲  ▲  ▲                                 1. clr_start  → FB 全クリア
   │  │  │  │  │                                 2. LCD 全面塗りつぶし (1 矩形)
   │  │  │  │  │                                 3. line_draw → 罫線 9 本
   │  │  │  │  │                                    (FB に 9 本 + LCD に 9 矩形)
   │  │  │  │  └─ write: dot_field → 20 個の 2x2 点
   │  │  │  │           (FB と LCD の両方)
   │  │  │  │
   │  │  │  └─ write: line_draw → game_ctrl
   │  │  │        （ゲーム開始で切替）
   │  │  │
   │  │  └─ read: dot_field（点のワードの読み戻し）
   │  └─ read: line_draw（部分ワードの読み戻し）
   │          → game_ctrl（描く前のピクセル判定）
   │
   │  └── ✗ LCD へのスキャンアウトは無い（Frame Buffer は表示に使わない）
   │
   └─ 罫線/点/自機 → 矩形リクエスト (x0,y0,x1,y1,+RGB565)
        │
        ▼  fill / line_draw / dot_field / game_ctrl の 4 系統を mux
   lcd_ili9341_ctrl ─ CASET/PASET/RAMWR ─ SPI ─► ILI9341 (GRAM に保持)
```

* リセット直後の起動シーケンスで、**FB 全クリア → 画面全体をオレンジで塗る
  → 罫線 9 本 → ランダムな点 20 個 → ゲーム開始**を順に行います。
  `line_draw` と `dot_field` は **`start` の 1 パルスで全部描く**ので、
  トップレベルが `start` を出すのはそれぞれ 1 回だけです。
* ゲーム開始 (`init_state == I_GAME_BEGIN`) で、書き込みポートと読み出し
  ポートが `line_draw`/`dot_field` から `game_ctrl` に切り替わります。
* **LCD への全画面転送はありません。** 矩形リクエスト 4 系統
  （全面塗りつぶし / 罫線 / 点 / ドット）を mux して
  `lcd_ili9341_ctrl` に渡します。同時に有効になる系統は無いので、
  調停ではなく単純な優先 mux です。
* Frame Buffer の読み出しレイテンシは **1 クロック**です
  （読み出しポートが 1 本になったため。Step 5 まではピクセル変換段が
  あったので 3 クロックでした）。

## 3. フレームバッファ（当たり判定専用）

仕様書 (`prompt.txt` の Architecture) の「320x240 の Frame buffer を作る
（色深度は 1 ビット）」に対応します。

**Step 6 以降、この RAM は LCD の表示には使いません。** ILI9341 が自分の
GRAM に画像を保持するため、表示は矩形コマンドで直接書き込みます。
Frame Buffer の役割は次の 2 つだけです。

* 罫線（壁）と自機の軌跡を覚えておく
* 描く前に次のピクセルを読み、**既に描かれていれば GAME OVER**

| 項目 | 値 |
|---|---|
| サイズ | 320 x 240 = 76,800 bit |
| 構成 | 2400 ワード x 32 bit (32 ピクセルを 1 ワードにパック) |
| 実装 | M9K (`ramstyle = "M9K, no_rw_check"`) x **1 ブロック** |
| ワードアドレス | `y*10 + x/32` |
| ビット位置 | `x % 32` |
| 読み出しポート | 1 本（同期式、レイテンシ **1 クロック**） |
| 書き込みポート | 1 本 |

**Step 5 より小さくなりました。** Step 5 までは LCD のスキャンアウト用に
2 本目の読み出しポートが必要で、Quartus が「書き込み 1 + 読み出し 2」を
実現するために RAM 全体を 2 ブロックに複製していました
(153,600 bit / M9K 32 ブロック)。表示に使わなくなったことで
「書き込み 1 + 読み出し 1」の素直な Simple Dual Port になり、
**76,800 bit / M9K 16 ブロック** とほぼ半減しています。

読み出しポートは**同期式** (出力レジスタあり) です。
`assign rd_data = mem[rd_addr];` のような非同期読み出しにすると、
Quartus が M9K を推論できずレジスタで RAM を作ろうとして
(76800 bit は 10M08 に収まらないため) コンパイルが失敗します。

なお、**読み出しと書き込みが同じクロックで同じワードに起きた場合、
読み出しには古いデータが返ります** (両方ノンブロッキングなので、
書き込みの更新より読み出しのサンプリングが先)。ゲームは
「読む → 数クロック後に書く」なのでこの状況にはなりません。

`lcd_test_top` の起動 FSM は `I_DRAW` で **`start` を 1 回だけ**出し、`busy` が下がるのを待って 1 クロックを挟んでからゲームを開始します。

```
I_CLEAR → I_CLEAR_WAIT → I_FILL → I_FILL_BUSY → I_FILL_WAIT → I_FILL_GAP
FB クリア  クリア完了     LCD 全面塗りつぶし要求  lcd_active 待ち   転送完了待ち

 → I_DRAW → I_DRAW_BUSY → I_DRAW_WAIT → I_DRAW_GAP → I_READY → I_GAME_BEGIN
    start=1   busy 待ち      busy 終了待ち   1clk 待ち     ゲーム開始パルス
```

**注意:** `line_draw` は 1 つの `start` でテーブル全体を描くので、
線の本数だけ `start` を出すと全線を 9 回描くことになります
(同じピクセルなら結果は同じですが、描画を条件分岐させたくなった時に
壊れます)。「1 start = テーブル全体」を守ってください。

## 3.1 線の描画 (`line_draw.sv`)

`line_draw` は線 1 本につき**2 か所**に書きます。

| 出力先 | 単位 | 理由 |
|---|---|---|
| Frame Buffer | 32 ピクセル (1 ワード) 単位の read-modify-write | 当たり判定モデル |
| LCD | **線 1 本 = 1 矩形リクエスト**（行単位） | 表示 |

Frame Buffer 側は横方向に 32 ピクセルを 1 ワードにパックしているので、
水平線は **1 ピクセルずつではなく 1 ワード単位の read-modify-write** で
描くのが速いです。

| 位置 | 処理 |
|---|---|
| 線の両端を含むワード | `rd_data | mask` を書き込む (部分マスク) |
| 中間のワード (全部線) | mask が全 1 になり、同じ `rd_data | mask` で書き込み |

書き込みは常に `rd_data | mask` なので、線の始点・終点を含むワードに
元からあったピクセルはそのまま残ります。つまり **同じ行に 2 本以上の線を
重ねて描いても壊れません**。

LCD 側は線ごとに 1 回、`lcd_valid` / `lcd_ready` のハンドシェイクで
矩形リクエストを出します。リクエストは受理されるまで保持します。

> **実装上の注意:** `lcd_valid` をアサートする状態と、`lcd_ready` を待つ
> 状態を**別々に**しています。1 つの状態で「アサートして、受理されたら
> クリア」と書くと、`lcd_valid` はレジスタなので**同じクロックで
> セットとクリアが起きて後勝ちになり、0 クロックしか立たない**ためです
> (不具合 #18)。

### 線のテーブル

Step 3 では 1 本だけだった線を**テーブル**にしました。線のリストは
パラメータの定数配列で与えます。

```systemverilog
parameter int N_LINES = 9,
parameter int LINE_X0 [N_LINES] = '{  0,  40,   0,  40,   0,  40,   0,  40,   0},
parameter int LINE_X1 [N_LINES] = '{279, 319, 279, 319, 279, 319, 279, 319, 279},
parameter int LINE_Y  [N_LINES] = '{ 25,  50,  75, 100, 125, 150, 175, 200, 225},
```

`start` を 1 回パルスするとテーブル全体を順に描き、全部終わるまで
`busy` が High のままです。線ごとにインスタンスを増やす実装も考えられますが、
テーブル方式なら**線の本数を `N_LINES` と 3 つの配列を増やすだけで変えられ**、
書き込みポートの調停コードも不要です (描画は起動時に 1 回だけなので)。

幾何情報は描く線の番号でテーブルから引く (小さな mux)、ビットマスクは
可変シフト 2 回で作ります。

```
mask = (全1 << lo) & ~(全1 << (hi+1))
lo = 最初のワードなら X0%32、それ以外は 0
hi = 最後のワードなら X1%32、それ以外は 31
```

32bit 値を 32 以上シフトすると 0 になるので、`hi=31` (上側カットなし) と
`lo=0` (下側カットなし) がそのまま正しく表現できます。

### 制限

| 項目 | 制限 | 理由 |
|---|---|---|
| 線の本数 | `N_LINES <= 16` | 線番号カウンタが 4 bit |
| 線の長さ / 横幅 | `FIELD_W <= 512` | 行内ワード番号が 4 bit |
| 空の線 (`X0 > X1`) | 描かずにスキップ | 行末を越えて書き込むのを防止。LCD にも出さない |
| `X1` が画面幅を越える | `FIELD_W-1` にクランプ | 次の行に漏れるのを防止 |

## 3.2 LCD への書き込み (`lcd_ili9341_ctrl.sv`)

ILI9341 は自分の GRAM に画像を保持するので、**変化した部分だけ**を
矩形コマンドで書きます。

```
wr_valid / wr_ready           1 件のリクエスト (受理されるまで保持)
wr_x0, wr_y0, wr_x1, wr_y1    含まれる範囲 (inclusive)
wr_color                      RGB565 (単色)
```

すると次のコマンド列を SPI で送ります。

```
CASET  x0 x1       2A と 4 バイト
PASET  y0 y1       2B と 4 バイト
RAMWR              2C
+ w*h ピクセル      16 bit/ピクセル、行優先 (列が速い)
```

| 用途 | ウィンドウ | ピクセル数 |
|---|---|---|
| 背景の塗りつぶし | (0,0)-(319,239) | 76,800 |
| 罫線 1 本 | (x0,y)-(x1,y) | 最大 320 |
| 動く線の 1 ドット | (x,y)-(x,y) | 1 |

ウィンドウが単色なので、**ピクセルごとにメモリを読む必要はありません**
(色は `wr_color` の固定値)。そのため転送中のデータパスはカウンタだけです。

1 回の書き込みのバイト数は `11 + 2*w*h` です。
画面全体でも 153,611 バイトで、これは**起動時に 1 回だけ**です。
Step 5 まではこれと同じ量を**毎フレーム**送っていました。

`CS` は書き込みごとに High に戻し、次のコマンド列まで
`CS_GAP_CYCLES` (32 clk) 待ってパネルに区切りを見せます。

## 3.3 疑似ランダムな点 (`dot_field.sv`)

初期化処理の最後に、**2x2 の点を 20 個**、疑似ランダムな位置に描きます
(`prompt.txt` #5)。

```
start / busy        1 パルスで N_DOTS 個をまとめて描く
X_MIN/MAX, Y_MIN/MAX  位置の範囲 (Y はパネルに合わせてクランプ)
DOT_W / DOT_H       点のサイズ
SEED                LFSR の初期値 (0 以外)
```

### 疑似ランダム数列 (LFSR)

32bit の**最大長 LFSR** (Galois 型、右シフト、タップ 32/22/2/1) を使います。
シフトレジスタと 1 個の XOR だけで、周期 $2^{32}-1$ の数列が得られます。

$$
f = q_{31} \oplus q_{21} \oplus q_1 \oplus q_0, \qquad
q \leftarrow \{q_{30:0}, f\}
$$

全 0 は固定点なので、シードは 0 以外の定数 `DOT_SEED` です。

### 座標の決め方 (棄却サンプリング)

LFSR を 1 回進めた後の下位ビットを候補にします。

```
X 候補 = lfsr_next[8:0]   (0..511)
Y 候補 = lfsr_next[7:0]   (0..255)
```

候補が範囲外なら**もう一度進めてやり直します**。除算も剰余演算も使いません。

| 方法 | 必要な回路 | 分布 |
|---|---|---|
| **棄却サンプリング (採用)** | 比較器のみ | 範囲内で**一様** |
| 剰余 `%` | 除算器 | 一様 |
| クランプ | 比較器のみ | **端に偏る** |

最大長 LFSR は 9bit/8bit の全てのパターンを巡回するので、
**必ず範囲内の候補に到達します** (無限ループしない)。
X は 317/512 ≈ 62 %、Y は 237/256 ≈ 93 % の確率で当たるので、
期待試行回数はそれぞれ約 1.6 回・1.08 回です。

### Y の範囲がクランプされる理由

`prompt.txt` の指定は (2,2)-(318,318) ですが、パネルは 320x240 です。
Y=318 は画面外なので、`Y_MAX` は `FIELD_H - DOT_H = 238` にクランプします
(2x2 の点が全部入る最後の行)。X は 318 以下なので 320 幅にそのまま収まります。

### 描き方

点は**ピクセル単位**でフレームバッファに書きます (2x2 = 4 ピクセル)。
1 ピクセルは「ワードを読む → 1 bit を OR する → 書き戻す」の 3 クロックです。

同じワードに点の 2 ピクセルが入る場合 (点がワード境界をまたぐ場合) は、
そのワードを 2 回読み書きします。**OR は冪等**で、2 回目の読み出しは
1 回目の書き込みが見えている (間に 3 クロックあるため) ので、正しく動きます。

> 点の矩形は `dx`/`dy` の 2 つのカウンタで走査します。線形のピクセル番号を
> `DOT_W` で割る方法は除算器が必要になるため使っていません。
> この方法なら DOT_W / DOT_H が 2 の冪でなくても動きます
> (`tb_dot_field` で 1x1 と 3x3 も検証しています)。

点の数は最大 32 個 (ドットカウンタが 5 bit) です。

## 3.4 ゲーム本体 (`game_ctrl.sv`)

`start` を受けたら 1 ドットずつ線を伸ばします。
ドットの間隔は `STEP_MS` をフレーム周期の整数倍に切り上げた値です
(§5.2 のフレーム同期)。
1 ドットごとの手順は次のとおりです。

```
G_TEST  : 次に進みたいピクセルのアドレスを提示       (0.1)
G_WAIT  : フレームバッファの登録済み読み出しを待つ   (0.2)
G_DRAW  : データが有効なのでビットを見る             (0.3)
            ・0 なら FB に 1 を書いて G_LCD へ
            ・1 なら 何も書かずに GAME OVER
G_LCD   : LCD に 1x1 の矩形リクエストを出す          (ドット単位で描画)
G_LCDW  : 受理されるまで保持
G_STEP  : 待って頭を 1 ドット進める                  (STEP_MS)
```

1 ドットにつき **書き込み先が 2 か所**あります。

| 出力先 | 内容 | 役割 |
|---|---|---|
| Frame Buffer | そのピクセルのビットを 1 に | 当たり判定モデル（次のドットの判定に使う） |
| LCD | `(x,y)-(x,y)` の 1x1 矩形 | 表示 |

フレームバッファの読み出しは**同期式**で、レイテンシは **1 クロック**です
(読み出しポートが 1 本になったため `G_WAIT` は 1 状態)。この間もアドレスは
変わらないので、`G_DRAW` で書くアドレスは「判定したピクセルそのもの」に
なります。

> **実装上の注意:** `G_LCD` と `G_LCDW` を分けているのは、`lcd_valid` が
> レジスタで、1 状態で「アサート + 受理されたらクリア」と書くと
> 0 クロックしか立たないためです (不具合 #18)。

### 方向の決め方

```systemverilog
// 横方向: x=0 / x=319 にぶつかったら反転し、1 ドット戻る
hit_hi = dir_r && (x == 319);   hit_lo = !dir_r && (x == 0);
if (hit_hi || hit_lo) begin  dir_r <= ~dir_r;  x <= dir_r ? x-1 : x+1;  end
else                       begin                x <= dir_r ? x+1 : x-1;  end

// 縦方向: ボタンのレベルで決まる（ルール上、反転はしない）
y <= btn ? ((y == 0)   ? 0   : y-1)
         : ((y == 239) ? 239 : y+1);
```

ぶつかったときに**1 ドット戻す**ので、頭が画面外に出ることはありません
(x=319 にいるときに 320 へ進む、ということが起きない)。

### このゲームの実際の挙動（重要）

縦方向はルール上反転しないので、**y は上下端に張り付いたまま横移動を
続けます**（クランプ）。そのため実際には:

* **(1,1) から右に伸びると、最初に出会うのは y=25 の壁（座標 (25,25)）**
  で、そこで GAME OVER になります。25 ≦ 239 なので y はまだ余裕があり、
  上下端には達しません。
* **x=319 での反転は起きます**（例えば (315,10) から始めれば 4 ドットで
  到達）。ただし反転後は同じ行を戻るので、自分の線に当たってすぐ終わります。
* **x=0 での反転は (1,1) から右向きでは絶対に起きません**。斜めに進むと
  x と y は同じ速さで進み、画面は横長 (320 > 240) なので、x が左端に
  届くより先に y が上下端に張り付き、その後は右に進むだけだからです。
  この分岐は `START_DIR_R = 1'b0` (左向きに開始) で動作確認しています。

`y` をクランプしているのは「画面外に書かない」ためです。クランプせずに
y をそのまま進めると、y が画面の高さを越えた瞬間に**別の行のピクセルを
壊す**ことになります。

### 起動シーケンスとの受け渡し

`game_ctrl` は `G_IDLE` の間、読み出しアドレスを動かさず書き込みも
しません。トップレベルは `I_GAME_BEGIN` で書き込みポートと読み出し
ポートを切り替え、同時に `game_start` をパルスします。

## 4. 色とパラメータ

`lcd_test_top` のパラメータで変更できます。

| パラメータ | 既定値 | 意味 |
|---|---|---|
| `COLOR_BIT0` | `16'hFD20` | 背景の色 (オレンジ)。画面全体の塗りつぶしに使う |
| `COLOR_BIT1` | `16'hF800` | 罫線と動く線の色 (赤) |
| `COLOR_DOT` | `16'hF81F` | ランダムな点の色 (紫 = マゼンタ) |
| `DOT_N` | `20` | 点の個数 |
| `DOT_W` / `DOT_H` | `2` / `2` | 1 つの点のサイズ (ドット) |
| `DOT_X_MIN/MAX` | `2` / `318` | 点の位置の範囲 (X) |
| `DOT_Y_MIN/MAX` | `2` / `318` | 点の位置の範囲 (Y)。`238` にクランプされる |
| `DOT_SEED` | `32'hACE1_2345` | LFSR の初期値 (0 以外であること) |
| `STEP_MS` | `40` | 動く線が 1 ドット伸びる時間の**最小値** (ms) |
| `LOCK_TO_FRAME` | `1'b1` | 1 フレーム = 整数ドットに自動追従させる (後述) |
| `FRAME_PERIOD_MS` | `250` | ドット周期を丸める基準の周期 (ms) |
| `START_X` / `START_Y` | `1` / `1` | 動く線の開始座標 |
| `N_LINES` | `9` | 罫線の本数 |
| `LINE_X0[i]` | `{0,40,0,40,...}` | 各罫線の開始 X |
| `LINE_X1[i]` | `{279,319,...}` | 各罫線の終了 X |
| `LINE_Y[i]` | `{25,50,75,...}` | 各線の Y |

Frame Buffer は 1 bit しか持たないので、`COLOR_BIT0` / `COLOR_BIT1` は
**LCD に送る色**であり、Frame Buffer には色は入りません。ピクセルが
「描かれている / いない」の 1 bit だけです。

RGB565 なので、赤=R[15:11], 緑=[10:5], 青=[4:0] です。
例えば 8bit の (R,G,B) から作るには
`{R[7:3], G[7:2], B[7:3]}` を使います。
`16'hF800` は赤 100%、`16'hFD20` はオレンジ (R=31, G=41, B=0) です。

## 5. タイミング

### 5.1 書き込み量（Step 6 で激減）

Step 6 の変更で、**SPI に流れるデータ量が桁違いに減りました。**

| 場面 | Step 5 まで | Step 6 |
|---|---|---|
| 1 回の全画面転送 | 153,611 バイト | — |
| 転送回数 | **毎フレーム (約 6.7 回/秒)** | — |
| 起動時の全面塗りつぶし | （全画面転送に含まれる） | 153,611 バイト × **1 回** |
| 罫線 1 本 | （全画面転送に含まれる） | 11 + 2×320 = 651 バイト × 9 本 |
| 動く線 1 ドット | （全画面転送に含まれる） | 11 + 2×1 = **13 バイト** |
| 静止中の通信量 | 1,034,000 バイト/秒 | **0** |

Step 5 までは SPI が 100 % 埋まっており、それが
「6.7 fps が上限」という制約になっていました。Step 6 では
**変化したときだけ書き込む**ので、この制約自体が消えています。

1 回の書き込みのバイト数は次の式です。

$$
\text{bytes} = 11 + 2 \times (\text{x1} - \text{x0} + 1) \times (\text{y1} - \text{y0} + 1)
$$

11 バイトはヘッダ (`2A` + 4 + `2B` + 4 + `2C`) です。

### 5.2 ドット周期（1 フレーム = 整数ドット）

ドットの間隔は `STEP_MS` を「最小値」として、**基準周期の整数倍に
切り上げ**ます (LOCK_TO_FRAME)。丸めないと、1 回のパネルリフレッシュに
入るドット数が 0,0,1,0,1… とばらついて、線が等速に見えません。

$$
\text{period} = \lceil \text{STEP\_MS} / \text{FRAME\_PERIOD\_MS} \rceil \times \text{FRAME\_PERIOD\_MS}
$$

| `STEP_MS` | `FRAME_PERIOD_MS` | 丸め | 実効周期 |
|---|---|---|---|
| 40 | 250 | ceil(40/250) = 1 | 250 ms |
| 250 | 250 | ceil(250/250) = 1 | 250 ms |
| 300 | 250 | ceil(300/250) = 2 | 500 ms |
| 800 | 250 | ceil(800/250) = 4 | 1000 ms |

つまり「基準周期の整数倍」にしか設定できないので、
`FRAME_PERIOD_MS = 250` ならドットは 250 / 500 / 750 … ms 刻みです。
既定 (`STEP_MS = 40`) は最小値の 1 周期 = 250 ms に丸められます。

> **Step 6 での意味の変化:** Step 5 ではこの周期は「実際のパネル
> リフレッシュ周期」でした (全画面転送が律速)。Step 6 では全画面転送が
> 無いので、`FRAME_PERIOD_MS` は**ドット速度を決めるための基準値**として
> 使います。ILI9341 自身は約 70 Hz でリフレッシュしているので、
> パネル側の見え方は 250 ms のドット周期に対して十分に速いです。

丸めはパラメータ式（整数の四則演算のみ）で行うので、
シミュレーション・合成の両方で同じ値になります。
`LOCK_TO_FRAME = 1'b0` にすると丸めをせず `STEP_MS` そのままになります
（規則そのものを検証するテストベンチはこちらを使います）。

### 5.3 SPI クロック（有理分周）

SCK は次の比で決まります。

$$
f_{sck} = f_{clk} \times \frac{\text{SCLK\_HALF\_DEN}}{2 \times \text{SCLK\_HALF\_NUM}}
$$

整数分周だと 50 MHz からは 25 / 12.5 / 8.33 / 6.25 MHz しか作れず、
データシート上限の **10 MHz が作れません**。そこで分周器を有理数にしました。
`NUM=5, DEN=2` で半周期 2.5 clk = 正確に 10 MHz になります。
累算器が半周期ごとに端数を繰り越すので、この設定では
**Low が 3 clk・High が 2 clk**（bit = 5 clk）となり、平均が正確に
10 MHz になります。どちらの半周期も最小 2 clk (40 ns) なので、
パルス幅の規定も満たします（`tb_spi_clk` で実測・確認済み）。

| `NUM` | `DEN` | SCK | 備考 |
|---|---|---|---|
| 2 | 1 | 12.5 MHz | データシート上限超え。比較用 |
| **5** | **2** | **10 MHz** | **既定値。データシート上限** |
| 1 | 1 | 25 MHz | 規定外。動作確認用 |

`HALF_DEN = 1` は従来の整数分周と同じなので、既存の設定はそのまま動きます。

| 項目 | 値 | 備考 |

### テスト内容

**`tb_framebuffer`** — 当たり判定用 RAM を検証

* ワードアドレスが `y*10 + x/32`、ビットが `x%32` であること
  (全 76800 ピクセルを走査)
* 読み出しポートが**同期式でレイテンシちょうど 1 クロック**であること
  (これが M9K 推論の条件)
* 同じクロックで同じワードを読み書きした場合、読み出しには
  **古いデータ**が返ること
* 全クリアが 2400 ワードすべてを 0 にし、読み出しポートからも
  0 が返ること

を検証します (153,604 チェック)。

> Step 5 まであった「ピクセル → RGB565 変換」の検証は、
> `framebuffer_pixel_src` 自体を削除したため無くなりました。

**`tb_line_draw`** — 線描画を 10 ケースで検証。各ケースは線テーブルを描き、

* **フレームバッファ 2400 ワード全部**をソフトウェア参照モデルと比較
  (線以外の場所への誤書き込みを検出)
* **LCD に出す行リクエスト**を全部収集して、線テーブルと比較
  (本数・範囲・色。空の線は出さない、`X1` はクランプ)

します。LCD 側は `lcd_ready` を時々落として、**受理されるまで
リクエストが保持される**ことも確認します。

| ケース | 何を検証するか |
|---|---|
| `(0,15)-(319,15)` | 全幅。両端のマスクが全 1、10 ワード全部を書き込み |
| `(17,20)-(301,20)` | 両端がワードの途中 → 部分マスクのパス |
| `(5,40)-(10,40)` | 始点と終点が同じワード |
| `(31,60)-(32,60)` | ワード境界をまたぐ (bit31 → bit0) |
| `(0,239)-(319,239)` | 最終行 (最高アドレス) |
| **設計と同じ 9 本** | テーブル全体を順に描けること。1 ピクセルの線も含む |
| **同じ行に 2 本 (重なり)** | `rd_data | mask` の OR セマンティクス |
| **16 本** | 線番号カウンタの上限まで使えること |
| **空の線 (X0 > X1) を混ぜる** | 空エントリを飛ばして次の線に進めること |
| **`X1=400` (画面幅越え)** | 列 319 で止まり、次の行に漏れないこと |

**`tb_dot_field`** — ランダムな点 (`dot_field.sv`) を 7 ケースで検証。

疑似乱数は**テストベンチ側に同じアルゴリズムを実装**して検証します。
TB がシード・多項式・棄却ルールを持ち、**RTL が出した位置が
ソフトウェアモデルの予測と 1 個ずつ一致するか**を比べます。
これで「乱数っぽく見えるが実は違う数列」を検出できます。

| 検証 | 内容 |
|---|---|
| 個数 | LCD リクエストがちょうど `N_DOTS` 個 |
| 形 | 各リクエストが `DOT_W x DOT_H` (`x1=x0+W-1`, `y1=y0+H-1`) |
| 範囲 | 全点が `(X_MIN,Y_MIN)`-`(X_MAX,Y_MAX)` 内で、パネルからはみ出さない |
| **数列** | 全点の位置が**ソフトウェアモデルの予測と一致** |
| バッファ | 全 2400 ワードが「点のピクセルだけ 1」と一致 |
| 多様性 | 全点が同じ位置でない、X も Y も変化する (固定値や単純カウンタを排除) |
| 再現性 | 同じ SEED で 2 回描くと**同じ順序**になる (毎回シードし直す) |

ケースは次の 7 個です。

| ケース | 内容 |
|---|---|
| 設計と同じ 20 個 2x2 | 本番の設定。**2 回描画して再現性も確認** |
| 同じ設定・別インスタンス | 同じ SEED なら別インスタンスでも同じ最初の点 |
| SEED を変更 | 数列が変わる |
| 8 個の 1x1 | `DOT_W=DOT_H=1` (1 ピクセル/点) |
| 6 個の 3x3 | `DOT_W=DOT_H=3` (9 ピクセル/点) |
| 狭い範囲 `(10,200)-(20,210)` | 棄却サンプリングが何度もやり直す必要がある場合 |
| Y=318 を指定 | パネル高さ 238 にクランプされ、はみ出さない |

> **3x3 のケースが実際に設計ミスを見つけました。** 最初の実装は 2x2 専用で、
> `x1 = x0 + 1` と `pix_i[0]`/`pix_i[1]` というビット選択でピクセルを
> 走査していました。この形だと `DOT_W=3` で `x1` が 1 ドットしか
> 進まず、点が 2x2 のままになります。`dx`/`dy` のカウンタに直して、
> 任意のサイズで正しく動くようになりました。

**`tb_game`** — ゲームルール (`game_ctrl.sv`) を 8 ケースで検証。各ケースは
実際の `framebuffer` を使うので、「すでに描かれているか」の判定は本物の
メモリに対して行われます。

手法: (1) ルールをそのまま実装したソフトウェア参照モデルで軌跡を計算し、
(2) その結果をフレームバッファに書き込み、(3) DUT を走らせて
**書き込み回数** を数え、(4) 頭の座標・`game_over`・**全 2400 ワード**・
**LCD に出す 1x1 リクエストの列**を参照モデルと比較します。
書き込み回数を数えるのがポイントで、何も障害物がないとき DUT は
自分では止まらないので `game_over` を待つとハングします。
同じカウンタで「衝突したドットは描かれず、LCD にも送られない」ことも
確認できます。

| ケース | 何を検証するか |
|---|---|
| ボタン離す | (1,1) から右下へ 1 ドットずつ |
| ボタン押す | 縦方向が逆になり、y=0 に張り付いて右へ進む |
| **x=319 で衝突** | 横方向だけ反転し、縦は進み続ける |
| **x=0 で衝突** | 横方向だけ反転する（`START_DIR_R=0` で左向き開始） |
| ボタン途中で押す/離す | 縦方向がボタンに追従する |
| **障害物に衝突** | 軌跡上のピクセルを置いて GAME OVER |
| **罫線 9 本** | (1,1) から右下へ進み (25,25) で GAME OVER |
| **反転して自分の線に衝突** | 反転後の再衝突でも GAME OVER |

**`tb_rect_write`** — LCD の矩形書き込み (`lcd_ili9341_ctrl.sv`) を
実 SPI で検証します。SPI バイトを全部受信して (D/C レベル付きで)
記録し、期待するコマンド列と比較します。

| 検証 | 内容 |
|---|---|
| 初期化 | 67 バイト (SWRESET → SLPOUT → … → MADCTL=28 → … → DISPON) |
| 矩形 `5x3 @ (10,20)` | `2A 00 0A 00 0E` `2B 00 14 00 16` `2C` + 15 ピクセル |
| **1x1 ドット @ (7,9)** | 同じヘッダで x0=x1=7, y0=y1=9、ピクセル 1 個 |
| `x1 = 319` | CASET の上位バイトが `01`、下位が `3F` |
| **バス停止** | その後 400 us 通信が無いこと (フレーム再送が無い) |
| CS 区切り | 初期化 1 列 + 書き込み 3 列 = 4 トレイン |

> この TB は以前の `tb_orange` (全画面スキャンアウトの検証) を置き換えた
> ものです。全画面転送が無くなったので、代わりに
> 「**行単位・ドット単位の矩形書き込み**」と「**静止時は通信しない**」を
> 検証しています。

**`tb_spi_clk`** — SPI 分周器 (`spi_byte_master.sv`) を検証。
SCK の周期と High/Low の最小幅を実測し、パラメータ通りの周波数に
なっていることを確認します。

| パラメータ | 期待 | 実測 |
|---|---|---|
| `NUM=5 DEN=2` | 10 MHz (bit 5 clk) | 5.000 clk / 10.00 MHz |
| `NUM=2 DEN=1` | 12.5 MHz (bit 4 clk) | 4.000 clk / 12.50 MHz |

有理由分周では Low が 3 clk・High が 2 clk と非対称になりますが、
**平均** が 5 clk/bit になり、どちらの半周期も最小幅を満たすことを
確認しています。

> 1 バイトだけ送って測るのがポイントです。バイトとバイトの間には
> FSM が idle に戻る 1 clk の隙間があるため、複数バイトを平均すると
> 1 clk/バイトだけ周期が長く出ます (実際、最初の版はこれを
> 5.125 clk と測定して誤 FAIL になりました)。

## 9. 動作確認時の注意

* **画面が真っ暗 / 何も出ない** — LED で切り分けてください。
  `led` が点灯していれば初期化完了、`led0` が点灯していれば
  全面塗りつぶしと罫線の描画が完了してゲームが始まっています。
  `led1` は **LCD に書き込みが完了するたびにトグル**します。
  書き込みは起動時とゲーム中 (ドットを描くたび) だけなので、
  **ゲームオーバー後は `led1` が止まります** (正常)。
  `led` が点灯しない場合は SPI が止まっているので、`lcd_cs` / `lcd_sck` /
  `lcd_mosi` / `lcd_dc` の配線を確認してください。
* **起動直後 1 秒くらい画面が真っ白/ちらつく** — 全面塗りつぶし
  (153,611 バイト = 約 1.4 秒) を送っている途中です。
  そのあと罫線が 1 本ずつ現れます。**異常ではありません。**
* **すぐ GAME OVER になる（`led2` が点灯）** — (1,1) から右下に伸びて
  y=25 の罫線に当たるので、正常でも **約 6 秒** (24 ドット x 250 ms)
  で GAME OVER になります。これは仕様通りです。最初の壁までの距離を
  変えたい場合は `LINE_Y[0]`（既定 25）を大きくしてください。
* **ボタンを押しても上に曲がらない** — ボタンは押している間だけ右上に
  なります。`led3` が点灯しているかでボタンが読めているか確認できます。
  極性が逆 (押すと `led3` が消える) なら、基板上のプルアップが無い可能性が
  あります。
* **線が 9 本揃わない** — `led0` が点灯しているのに線が揃わない
  場合は、`N_LINES` と 3 つの配列の要素数が一致しているか
  (不一致だとコンパイル時に型エラーになります)、
  空の線 (`X0 > X1`) が混ざっていないかを確認してください。
  Step 6 以降は**線も LCD の GRAM に残る**ので、
  「前に描いた線が消えない」なら起動時の全面塗りつぶしが
  終わる前に線を描いていることになります。
* **オレンジは出るが線が見えない** — `LINE_Y[0]` を画面中央付近 (例 120)
  に変えてみてください。線が 1 ドット幅なので、表示の向きや拡大設定に
  よっては見落とすことがあります。
* **線の位置がおかしい / 画面が回転している** — `MADCTL_VALUE` と
  Y 座標の向きの組み合わせです。`MADCTL_VALUE` (既定 `8'h28`) を
  `8'h48` / `8'h88` / `8'hE8` に変えて試してください。
* **RESX (LCD リセット)** — ピン表に RESX がないため、初期化は
  SWRESET コマンドのみで行っています。PMOD ボード側で RESX が
  プルアップされている前提です。もし別の GPIO に繋がっている場合は、
  そのピンを追加して数 ms High に保つ必要があります。
* **紫の点が 20 個見えない** — 点は**罫線の後ろ・ゲーム開始前**に描くので、
  `led0` が点灯する前に描き終わっています。`led0` が点灯しているのに点が
  少ない場合は、点が**罫線と重なっている**か、**別の点と同じ位置**に
  なっている可能性があります（重複は許容しています）。`DOT_SEED` を
  変えると配置が変わります。
* **点が画面の下半分に出ない** — `DOT_Y_MAX` は `FIELD_H - DOT_H = 238` に
  クランプされます。`prompt.txt` の指定は 318 ですが、パネルは 240 行です。
  全画面を使いたい場合は `DOT_Y_MAX` を 238 にしてください（既定と同じ）。
* **点の色が紫でない** — `COLOR_DOT` (既定 `16'hF81F`) を変更してください。
  紫 = 赤 + 青なので、R と B の両方のビットが立っている必要があります。
* **シミュレーションで「直したのに結果が変わらない」** — 一番嵌りやすい
  罠です。`vsim` は最適化した結果を `work/@_opt*` にキャッシュするので、
  **前回の実行が異常終了していると、`vlog` をやり直しても古い結果が
  使われる**ことがあります（RTL の修正が反映されない）。必ず
  `run_all.bat` / `run_one.bat` 経由で実行してください（実行前に `work` を
  削除します）。手動で `vlog` だけ叩いて `vsim` を繰り返す使い方は避けて
  ください。
* **色が違う** — `COLOR_BIT0` (背景) / `COLOR_BIT1` (罫線・自機) /
  `COLOR_DOT` (点) を変更してください。RGB565 のビット順が
  逆 (BGR) に見える場合は `MADCTL_VALUE` の bit3 (BGR) を反転してください。
* **表示が回転 / 鏡像** — `MADCTL_VALUE` (既定 `8'h28`) を
  `8'h48` / `8'h88` / `8'hE8` などに変えて試してください。
* **ボタン / スイッチの極性** — `debounce.sv` / `reset_sync.sv` は
  外部プルアップ (アイドル時 High) を前提にしています。基板上に
  プルアップがない場合は `lcd_game.qsf` の
  `WEAK_PULL_UP_RESISTOR` の行をアンコメントしてください。

## 10. 実装中に見つけて直した不具合 (記録)

### Step 1 で見つけたもの

1. **`pix_valid` がゲームフィールド外で出ていなかった**
   — y >= 200 の 40 行で `pix_valid` が出ず、LCD コントローラが
   フレーム途中で止まっていました (無限待ち)。フィールド外でも
   `pix_valid` を出し、色だけ情報表示色にするよう修正。
2. **初期化 ROM の delay エントリで `init_idx` が進んでいなかった**
   — SWRESET 後の delay で永久ループしていました。
3. **フレーム間に CS の High 区間がなかった**
   — `S_READY` で `lcd_cs <= 1'b1` の直後に `lcd_cs <= 1'b0` を
   書いていたため、非ブロッキング代入の後勝ちで CS が下がったままに
   なり、フレームが連続した 1 本のコマンド列として出力されていました。
   `S_FRAME_END` を追加して CS を 32 clk 以上 High に保つよう修正。
4. **フレームバッファのクリア完了前にフレームが始まる可能性**
   — `frame_seq` の `ready` に `!clr_busy` を追加。

### Step 2 で見つけたもの

5. **Quartus がフレームバッファを M9K に推論できずコンパイル失敗**
   — これが一番嵌ったところです。

   ```
   Info (276007): RAM logic "framebuffer:u_fb|mem" is uninferred due to
                  asynchronous read logic
   Error (276003): Cannot convert all sets of registers into RAM megafunctions
   ```

   `framebuffer.v` が `assign rd_data = mem[rd_addr];` (非同期読み出し)
   だったため、Quartus は M9K を使わず 76800 bit をレジスタで作ろうとして
   いました (10M08 には収まらないので即エラー)。
   **読み出しを同期式 (`rd_data <= mem[rd_addr];`) に変更**して解決。
   これでメモリビットが 76,800 (= 320x240) と正しく報告されます。

   注意: Step 1 では同じ非同期読み出しのまま何の警告も出ずに通りました。
   あれはフレームバッファが定数化されて消えていた (メモリビット 0) ためで、
   実際に RAM として残ったのは Step 2 が初めてです。
   **「メモリビット 0」は「推論成功」ではなく「消えた」サイン**でした。
6. **読み出しレイテンシが 2 → 3 クロックに増えた**
   — 上記の同期化で 1 クロック増えたため、`framebuffer_pixel_src` に
   パイプライン段を 1 つ追加し、`line_draw` には read data を待つ
   `WAITDATA` 状態を追加しました。
   TB 側も「ちょうど 3 クロック後に `pix_valid` が出る」検証に更新。

### Step 3 で見つけたもの

7. **`tb_line_draw` が time 0 で「PASS」と出ていた (テストの落とし穴)**
   — 線をテーブル化した際に気付いた、**シミュレーション自体の欠陥**です。
   ケースの完了フラグを `logic done[]` で宣言していたため、
   時刻 0 では値が `x` でした。TB の待ちループ

   ```systemverilog
   while (!done[i]) @(posedge clk);
   ```

   は `!x` が偽になるため**一度も待たずに抜け**、各ケース本体が 1 行も
   実行されないまま「PASS (5 cases)」と表示していました。
   修正は `bit done[]` (2 ステート) にして 0 から始めることと、
   全ケースが実際に完走したかを検証する行の追加です。
   **同じ形のテストは、機能が壊れていても PASS を返します。**
   `$finish` の時刻が 0 ps になっていたのが手がかりでした。
8. **起動 FSM が線の本数だけ `start` を出していた (`line_draw` の契約違反)**
   — `line_draw` を「1 パルス = テーブル全体を描画」にしたのに、
   `lcd_test_top` 側に線ごとのカウンタを残したまま「`busy` が下がる →
   次の `start`」を `N_LINES` 回繰り返す実装になっていました。
   このため**全 9 本を 9 回描画**していました。
   全線が同じピクセルを書くので画面上は正しく見えてしまい、
   シミュレーションでも検出できないタイプのバグです
   (描画を条件分岐させた瞬間に壊れます)。
   不要なカウンタを削除し、`start` を 1 回だけ出す形にして、
   モジュールの「1 start = テーブル全体」という契約を
   コードと README の両方に明記しました。
9. **x1 が画面幅を越える線が次の行に漏れる**
   — ワードアドレスが `row_base + x/32` なので、`X1` が 319 を越えると
   その行の最後のワードを越えて**次の行のワード**に書き込んで
   しまいます。`X1` を `FIELD_W-1` にクランプし、
   `tb_line_draw` に `(300,200)-(400,200)` のケースを追加しました。
10. **Quartus の幅切断警告 (Warning 10230)**
    — 上記のクランプを `(t_x1 > (FIELD_W-1)) ? (FIELD_W-1) : t_x1[8:0]`
    と書くと、32bit の `int` パラメータと 9bit のワイヤが混ざって
    「truncated value with size 32 to match size of target (9)」が出ます。
    さらに `int` は**符号付き**なので `t_x1 > FIELD_W` は
    符号付き/符号なしの比較になってしまいます。
    32bit 符号なしの定数を定義し、狭い側はその**スライス**で取る形に
    修正しました (`localparam logic [8:0] LAST_COL = LAST_COL_W[8:0];`)。

### Step 4 で見つけたもの

11. **起動 FSM が `busy` の立ち上がりを取り逃し、罫線がほとんど描かれずに
    ゲームが始まっていた（一番厄介だったバグ）**
    — ゲームを追加した後、`tb_orange` で「罫線 9 本が画面に無い」
    （期待 f800 のところが fd20）という失敗が出ました。

```
I_DRAW      : line_start <= 1;    // パルス
I_DRAW_WAIT : if (!line_busy) ... // busy が下がるのを待つ
```

    ところが `line_start` も `line_busy` も**レジスタ**なので、
    パルスを出した次のクロックでは `line_draw` はまだ `busy` を
    上げていません。したがって `I_DRAW_WAIT` の `!line_busy` が
    いきなり真になり、**描画が始まる前に**書き込みポートと読み出し
    ポート B を `game_ctrl` に渡してしまっていました。

    このバグが厄介なのは:
    * **エラーも警告も出ない**（Quartus も Questa も沈黙）
    * ゲーム側は正常に見える（実際、動く線は正しく描かれていた）
    * 画面上は「罫線が無い」だけなので、罫線のバグかと誤解しやすい

    修正は「`busy` が**上がるのを待つ**状態を 1 つ入れてから、
    下がるのを待つ」という 2 段構えです。

    ```
    I_DRAW      : line_start <= 1;
    I_DRAW_BUSY : if (line_busy)  → I_DRAW_WAIT   // 立ち上がりを待つ
    I_DRAW_WAIT : if (!line_busy) → I_DRAW_GAP    // 立ち下がりを待つ
    ```

    **教訓:** 「パルスを出した後、そのモジュールが busy を上げるまで」を
    確認せずに `!busy` を待つと、**1 クロックで素通りします**。
    非同期（組み合わせ）の strobe と違い、レジスタ出力の strobe は
    必ず 1 クロック遅れて反応することを前提に FSM を書く必要があります。
12. **フレームバッファの読み出しポートが 1 本では足りなかった**
    — ゲームは「描く前にピクセルを読む」ので、LCD のスキャンアウトとは
    別のタイミングで自前のアドレスが必要です。1 本のポートを時分割すると
    スキャンアウトが止まってしまいます。**ポート A（スキャン専用）＋
    ポート B（ゲーム/線描画）** の 2 本構成に変更しました。

    副作用として、**M9K が 1 ブロックから 2 ブロックに増えました**。
    M9K は読み出し 2 + 書き込み 1 ではなく「読み出し 2 + 書き込み 1 は
    不可」なので、Quartus が RAM 全体を複製して書き込みを両方に入れ、
    読み出しを 1 本ずつ担当させます。フィット結果のメモリビットが
    76,800 → 153,600 になるのはこれが理由です。
    42 ブロック中 32 ブロックで収まっているので問題ありません。

### Step 5 で見つけたもの

> Step 5 は「全画面転送をどう速くするか」の回でした。Step 6 で
> 全画面転送自体をやめたため、#16 と #17 の `frame_seq` は
> モジュールごと削除されています。記録として残しています。

13. **整数分周では 10 MHz が作れない**
    — 「データシート厳守で SPI クロックを 10 MHz に」という方針に対して、
    `50 MHz / (2N)` の整数分周で作れるのは 25 / 12.5 / 8.33 / 6.25 MHz だけで、
    **10 MHz は作れません**。PLL を追加すれば作れますが、そのためだけに
    PLL を入れるのは避け、分周器自体を有理数にしました。
    これはバグというより「素直に整数分周のままパラメータを変えるだけでは
    目的の周波数にならない」という設計上の罠です。

14. **カクカクの原因はフレームレートではなかった**
    — 最初に「フレームレートが低いのでは」と考えましたが、
    `tb_fps.sv` で測るとフレームは背中合わせで **SPI が 100 % 埋まって**
    おり（8.7 fps @12.5 MHz）、これ以上は仕様上上げられませんでした。
    実際の原因は `STEP_MS = 40 ms` とフレーム周期の**位相のずれ**で、
    1 フレームあたりのドット数が 0 枚か 1 枚とばらついていました。
    周波数を上げる前に、まず**何が速さを決めているのかを測るべき**だと
    分かった事例です。対策は `LOCK_TO_FRAME` による整数倍への丸めで、
    フレームレートは同じまま体感が改善しました。

15. **12.5 MHz はデータシート上限を超えていた**
    — Step 4 まで動いていた SCK = 12.5 MHz は、ILI9341 の書き込み
    上限 10 MHz を超えていました（実機では動いていましたが規定外です）。
    整数分周では 10 MHz が作れないため有理分周に変更し、あわせて
    1 ピクセルのコストを `16*bit_time + 11 clk` と確定させました。
    この式は実測値 (12.5 MHz で 115.2 ms) を再現し、既定の 10 MHz で
    139.8 ms になることを予測します。

16. **`MS_SCALE` を上げすぎるとフレームが止まる（シミュレーションが
    無言でハングする）**
    — `tb_fps` を速くしようと `MS_SCALE = 20000` にしたところ、
    フレームが 1 枚も出ず、エラーも出さずに 7 分以上停止しました。
    原因は `frame_seq.sv` の

    ```systemverilog
    localparam int PERIOD = ((CLK_FREQ_HZ/1000)/MS_SCALE) * FRAME_PERIOD_MS;
    ...
    if (timer == 32'(PERIOD) - 1)
    ```

    です。`(50_000_000/1000)/20000 = 0` になるため `PERIOD = 0` となり、
    比較値が `32'(0) - 1 = 0xFFFFFFFF` になって**永久に一致しません**。
    つまり「クロック数を 0 にする」という一見無害なパラメータが、
    `N-1` を終端条件に使っている回路を停止させます。

    対策は 2 つ入れました。
    * `frame_seq.sv` / `game_ctrl.sv` で `(CLK/1000)/MS_SCALE` が 0 なら
      1 にクランプ（実回路の保護）。
    * `tb_fps` の `MS_SCALE` を 1000 に変更（150 ms の待ちが 150 us に
      なり、140 ms のフレームに対して無視できる）。

    **教訓:** `N-1` と比較する回路は `N >= 1` を保証すること。
    テスト専用のスケール係数が分周比を 0 にしうることに注意。
    症状は「`Loading work.X` の直後でログが止まり、エラーが出ない」です。

17. **フレーム周期が `FRAME_PERIOD_MS + 転送時間` になっていた**
    — 元の `frame_seq` は「転送完了 → `FRAME_PERIOD_MS` 待つ → 次を要求」
    という**直列**の待ちでした。そのため実際のフレーム周期は

    ```
    周期 = FRAME_PERIOD_MS + 転送時間
    ```

    です。10 MHz では `150 + 140 = 290 ms` となり、フレームレートは
    わずか **3.4 fps** でした（Step 4 の 12.5 MHz なら
    `250 + 115 = 365 ms` = 2.7 fps）。

    **Step 4 の実測では気づけませんでした。** 当時の `tb_fps` は
    `MS_SCALE = 2000` を使っていたので `PERIOD` も 2000 分の 1
    (100 us) になり、待ちが実質 0 になっていたためです。つまり
    「転送 115 ms が背中合わせで動いている」という測定は正しいのですが、
    それは **実機のフレーム周期ではありませんでした**。
    `MS_SCALE` がテスト対象の周期まで縮めてしまうのが落とし穴です。

    対策として、`frame_seq` のタイマを**転送と並行**に走らせ、
    `FRAME_PERIOD_MS` 経過かつ `ready` の時に要求を出す形にしました。

    ```
    周期 = max(FRAME_PERIOD_MS, 転送時間)
    ```

    10 MHz・`FRAME_PERIOD_MS = 150` なら `max(150, 140) = 150 ms` で
    **6.7 fps** になります（修正前の約 2 倍）。
    タイマは `PERIOD-1` で飽和させ、`ready` になった最初のクロックで
    発火させるので、転送が `FRAME_PERIOD_MS` より長い場合でも
    待ちが二重にならず、転送時間そのものが周期になります。

> **注:** Step 6 で全画面転送自体をやめたため、#16 と #17 の
> `frame_seq` は**モジュールごと削除**されました。ここに残しているのは、
> 「テスト専用のスケール係数が分周比を 0 にしうる」という教訓
> (#16) が他のモジュールにも当てはまるためです。

### Step 6 で見つけたもの

18. **`lcd_valid` が 0 クロックしか立たず、リクエストが一切届かない**
    — これが一番嵌りました。`game_ctrl` の 1 つの状態で

    ```systemverilog
    G_LCD: begin
        lcd_valid <= 1'b1;         // セット
        ...
        if (lcd_ready) begin
            lcd_valid <= 1'b0;     // 同じクロックでクリア
            state     <= G_STEP;
        end
    end
    ```

    と書いてしまいました。**ノンブロッキング代入は後勝ち**なので、
    `lcd_ready` が High のとき `lcd_valid` は結局 **0 のまま**になります。
    つまり「アサートした瞬間にクリア」で、**一度も立たない**。
    その結果

    * `tb_game`: 全 8 ケースが「LCD dot requests = 0」
    * `tb_line_draw`: 16 本のケースが「LCD requests = 3」
      (16 本中 2 本しか出ていない)

    という、**書き込み回数だけが合わない**失敗になりました。
    Frame Buffer 側は完璧に通っていたので、一見「テストの
    期待値が間違っているのでは」と疑ってしまいましたが、
    実際は RTL の実バグでした。

    **修正:** アサート用の状態と待ち用の状態を分ける。

    ```
    G_LCD   : lcd_valid <= 1'b1;  → G_LCDW
    G_LCDW  : if (lcd_ready) lcd_valid <= 1'b0;
    ```

    `line_draw` も同じ形 (`L_LCD` / `L_LCDW`) にしました。
    **教訓:** 同じ `always` ブロック内で同じレジスタを
    「セット」と「条件付きクリア」すると、条件成立時に
    セットが消える。ハンドシェイクの valid は
    **アサートとクリアを別クロックにする**こと。

19. **ヘッダ FSM が無限ループ（`hdr_step` を 2 回インクリメント）**
    — LCD コントローラのヘッダ (CASET/PASET/RAMWR) を
    バイトごとに送る状態を 2 つに分けた際、`hdr_step` の
    インクリメントを

    * 「SPI を起動して次の状態へ」の側
    * 「送信完了を待って次へ」の側

    の**両方**に書いてしまいました。すると `hdr_step` は 1, 3, 5, 7, 9, 11…
    と **2 ずつ増える**ので、`hdr_step == 10` の判定
    (RAMWR を送り終えたかどうか) が**永遠に成立しません**。
    ヘッダを送り続けるので、パネルは初期化後もずっとコマンドを
    受け取り続け、シミュレーションは終わりません。

    気付き方: `vsim` が CPU を全く使っていないのに終わらない
    (ライセンス待ちと紛らわしい) ので、まず
    **`hdr_step` の進み方を疑う**べきでした。
    `tb_rect_write` が「初期化 67 バイト」でタイムアウトして
    教えてくれたので、そこで気付けました。

    **修正:** インクリメントは「送信完了を待つ」側の 1 か所だけ。
    **教訓:** カウンタは 1 か所でだけ進める。
    特に「起動側」と「完了側」に状態を分けたときに
    両方に `<= +1` を残しがちです。

20. **FSM の enum 幅が足りない (vlog-13003)**
    — 状態が 11 個になったのに `typedef enum logic [2:0]` (8 個まで) の
    ままでした。`S_DATA` 以降が表現できない、とコンパイルエラーで
    教えてくれます。FSM に状態を増やしたら enum の幅も見直すこと。

21. **読み出しと書き込みが同クロックのとき、読み出しは「古い」データ**
    (ドキュメントの誤り)
    — `framebuffer.v` のコメントに
    「書き込みポートが優先なので read-during-write は新しいデータが返る」
    と書いていましたが、**逆**でした。
    両方ノンブロッキング (`mem[wr_addr] <= ...` と
    `rd_data <= mem[rd_addr]`) なので、読み出しは書き込みが
    更新する**前**の値をサンプリングします。
    `tb_framebuffer` がこれを検出したので、コメントとテストの
    期待値を「古いデータ」に直しました。
    ゲームは「読む → 数クロック後に書く」なので実害はありませんが、
    **同じクロックで読んで書く設計にした瞬間にハマる**ところでした。

### Step 7 で見つけたもの

22. **`dot_field` が 2x2 専用だった（3x3 のケースが検出）**
    — 最初の実装は点の矩形を 2x2 前提で書いていました。

    ```systemverilog
    x1_c  <= x_cand + 9'd1;            // DOT_W が 2 である前提
    wire [8:0] px = x_c + {8'b0, pix_i[0]};   // pix_i の下位 2 bit を
    wire [7:0] py = y_c + {7'b0, pix_i[1]};   // x/y に振り分ける前提
    ```

    `DOT_W`/`DOT_H` というパラメータを用意しながら中身が固定だったため、
    `DOT_W=3, DOT_H=3` のケースで

    * 点が 1x1 のまま（`x1 = x0+1`）
    * バッファの上位ビットが立たない

    という失敗が出ました。`dx`/`dy` の 2 つのカウンタに直し、
    `x1_c <= x_cand + DW_LAST`、`px = x_c + dx_i` としたことで
    任意のサイズで正しく動くようになりました。
    **教訓:** パラメータを用意したら、**そのパラメータを変えたケースを
    必ずテストに入れる**こと。既定値だけで通るテストは、
    ハードコードを見逃します。

23. **古い `work` ライブラリが残り、RTL を直しても結果が変わらない**
    — #22 を修正したのに `tb_dot_field` の出力が**1 文字も変わらず**、
    同じ 32 エラーが再現しました。原因はコンパイルではなく環境です。

    * `vlog` は `work` ライブラリの**同じ設計ユニットを置き換えます**が、
      その前に `vsim` が**最適化 (`vopt`) した結果を `work/@_opt*` に
      キャッシュ**しています。前回の `vsim` が異常終了していると
      そのキャッシュが残り、再コンパイル後も古い最適化結果が使われます。
    * つまり **RTL を直しても、その変更が反映されない**ように見えます。
      症状は「エラーは変わらないが、コードは明らかに直っている」
      という矛盾で、タイムスタンプを比べるまで気付けません。

    **修正:** 実行前に `work` を丸ごと削除する。これを
    `run_all.bat` / `run_one.bat` の先頭に入れました
    (`if exist work rmdir /s /q work`)。

    **教訓:** 「直したのに結果が同じ」ときは、コードではなく
    **ビルドが本当に走っているか**を先に疑うこと。
    手動で `vlog` だけ叩いて `vsim` を繰り返す使い方は、
    この罠を踏みます。
